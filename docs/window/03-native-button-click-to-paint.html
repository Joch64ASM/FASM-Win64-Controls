Tutorial 03 · Window

Native Button: Click to Paint

Now we add the first real child control. The window starts clean with one normal native BUTTON. Clicking it changes application state, requests a repaint, and lets WM_PAINT decide what the parent displays.

1. One new idea: let the control talk to its parent

Tutorial 02 taught us how to paint Unicode text. This lesson deliberately starts from the clean shell again so the new concept is obvious: a child control sends a notification to its parent.

Nothing is painted when the program opens. The button is the only new visible object. Only after a click does the parent decide that the text should exist.

Program starts │ ▼ [ Paint Text ] │ │ click ▼ WM_COMMAND │ └─ BN_CLICKED │ ▼ TextVisible toggles │ ▼ InvalidateRect │ ▼ WM_PAINT │ ▼ DrawTextW

2. A BUTTON is another window

A native button is not a bitmap painted into the parent. It is its own child window, with its own HWND and a window procedure supplied by USER32.

mainCreateWindowExW — BUTTON
invoke CreateWindowExW, 0, ButtonClassName, _buttonPaintText,\
       WS_CHILD + WS_VISIBLE + WS_TABSTOP + BUTTON_BS_PUSHBUTTON,\
       0, 0, 0, 0,\
       [MainWindow], ID_BUTTON_DEMO, [wc.hInstance], 0

test    rax, rax
jz      error

mov     [hButton], rax

The class name is the system class 'BUTTON'. We do not register that class ourselves; Windows already owns it. We create an instance as a child of MainWindow.

Why no owner-draw yet?

This is intentionally a normal Windows button. USER32 still handles its standard behavior and painting. We first learn the control's message contract; custom appearance comes in the next lesson.

3. The control ID gives the parent a stable identity

The child has an HWND, but command notifications also carry a small control ID. This example assigns ID_BUTTON_DEMO when the button is created.

constantsbutton identity
ID_BUTTON_DEMO       equ 1001
BUTTON_BN_CLICKED    equ 0

The parent can therefore distinguish this button from other controls that may later send WM_COMMAND.

4. BN_CLICKED arrives inside WM_COMMAND

When the native button is activated, Windows sends WM_COMMAND to the parent. For a control notification, the low word of wParam contains the control ID and the high word contains the notification code.

WindowProcdecode WM_COMMAND
.wmcommand:
        mov     eax, dword [wparam]
        mov     ecx, eax

        ; LOWORD(wParam) = control ID
        and     eax, 0FFFFh
        cmp     eax, ID_BUTTON_DEMO
        jne     .default

        ; HIWORD(wParam) = notification code
        shr     ecx, 16
        cmp     ecx, BUTTON_BN_CLICKED
        jne     .default

The original lParam also identifies the sending child HWND. The ID is enough for this one-button lesson, so the handler stays focused.

5. The click changes state — it does not paint

The button click flips one application-owned value:

WM_COMMANDtoggle state
; 0 = hidden, 1 = visible
xor     dword [TextVisible], 1

This separation is important. WM_COMMAND describes an event. Our handler updates the program's state in response to that event; it does not borrow a DC and draw text immediately.

6. InvalidateRect requests a repaint

After the state changes, the parent client area no longer represents the current state. We mark it dirty:

WM_COMMANDrequest paint
invoke InvalidateRect, [hwnd], NULL, FALSE

InvalidateRect is not a call to PaintWindow. It adds the requested region to the window's update region. Windows later delivers WM_PAINT through the normal message system.

Event handling versus rendering

WM_COMMAND changes what the program means. WM_PAINT draws what that state currently looks like.

7. WM_PAINT renders the current state

The painting code simply asks whether TextVisible is zero. If it is, the text section is skipped. If it is nonzero, the DrawTextW work from Tutorial 02 is used.

PaintWindowconditional rendering
cmp     dword [TextVisible], 0
je      .skip_painted_text

invoke GetClientRect, [hwnd], textRect

mov     eax, [ScaledTitleHeight]
mov     [textRect.top], eax

mov     eax, [ButtonY]
sub     eax, [ScaledTextButtonGap]
mov     [textRect.bottom], eax

invoke SelectObject, [hdc], [hTextFont]
mov     rdi, rax

invoke SetBkMode, [hdc], TRANSPARENT
invoke SetTextColor, [hdc], PAINT_TEXT_COLOR
invoke DrawTextW, [hdc], _paintText, -1, textRect,\
       DT_CENTER + DT_VCENTER + DT_SINGLELINE

invoke SelectObject, [hdc], rdi

.skip_painted_text:

When the text is switched off, repainting the dark background removes the old pixels naturally. We do not need a special “erase this string” operation.

8. The native button owns its caption

The parent-painted text and the button caption are two different things. The button is a real HWND, so its own text is changed with the normal Unicode window API.

WM_COMMANDtoggle caption
cmp     dword [TextVisible], 0
je      .hide_text

invoke SetWindowTextW, [hButton], _buttonClearText
jmp     .request_repaint

.hide_text:
invoke SetWindowTextW, [hButton], _buttonPaintText

That gives the interaction a useful visible state: Paint Text becomes Clear Text, and vice versa.

9. A real child control receives WM_SETFONT

This is a useful contrast with Tutorial 02. Painted text has no HWND, so its HFONT is selected into an HDC. A button is a window, so we tell the control which font handle to use with WM_SETFONT.

UpdateButtonFontnative control font
mov     [hButtonFont], rsi
invoke SendMessageW, [hButton], WM_SETFONT, rsi, TRUE

The final TRUE asks the control to redraw after the font changes. USER32 stores the font handle, but it does not take ownership of our GDI object.

10. Child windows need layout — and DPI affects layout

A child HWND does not automatically remain centered when its parent resizes. WM_SIZE therefore calls LayoutButton.

WM_SIZElayout policy
.wmsize:
        call    LayoutButton
        invoke InvalidateRect, [hwnd], NULL, FALSE

The button dimensions and offset are recalculated from fixed 96-DPI design values. On WM_DPICHANGED the shell measurements and both fonts are rebuilt for the new monitor, while the recommended window rectangle from Windows is still honored.

11. The parent owns both HFONT objects

Window 1.4 now creates two fonts: one for parent-painted text and one for the child button. Both were created by this application, so both remain our responsibility.

WM_DESTROYfont cleanup
cmp     [hTextFont], 0
je      .no_text_font
invoke DeleteObject, [hTextFont]
mov     [hTextFont], 0

.no_text_font:
cmp     [hButtonFont], 0
je      .no_button_font
invoke DeleteObject, [hButtonFont]
mov     [hButtonFont], 0

Sending an HFONT to a control does not transfer ownership. That distinction becomes increasingly important as more controls and custom drawing are added.

12. What we learned

The first child control gives us the core Win32 control-notification pattern without hiding it behind a framework.

  • A native BUTTON is a real child window with its own HWND.
  • The system BUTTON class is already registered by Windows.
  • Buttons notify their parent with WM_COMMAND.
  • LOWORD(wParam) identifies the control and HIWORD(wParam) carries BN_CLICKED.
  • The click handler changes application state rather than painting directly.
  • InvalidateRect marks an update region and causes painting later.
  • WM_PAINT renders the current state.
  • A child HWND owns its caption, so SetWindowTextW changes the button text.
  • A real control receives its font through WM_SETFONT.
  • The application still owns an HFONT it created, even after sending it to a control.
  • Child HWND layout must be updated when the parent size or DPI changes.
