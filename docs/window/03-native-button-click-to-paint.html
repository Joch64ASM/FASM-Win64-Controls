Tutorial 03 · Window

Native Button: Click to Paint

Now we add the first real child control: a normal native Windows BUTTON. The button does not paint the lesson text itself. It sends a notification to its parent, the parent changes application state, and WM_PAINT renders that new state.

1. One new idea: let the control talk to its parent

Tutorial 02 taught us how to paint Unicode text with DrawTextW. For this lesson we deliberately start again from the clean shell, so the window initially contains no painted lesson text. The only new visible object is one normal native BUTTON.

Program starts │ ▼ [ Paint Text ] │ │ click ▼ WM_COMMAND │ └─ BN_CLICKED │ ▼ TextVisible toggles │ ▼ InvalidateRect │ ▼ WM_PAINT │ ▼ DrawTextW

This is our first complete control-notification loop: control event → parent message → application state → repaint.

2. A BUTTON is another window

A native Windows button is not drawn directly into the parent HDC. It is a child window created from the system class named BUTTON.

mainCreateWindowExW
invoke CreateWindowExW, 0, ButtonClassName, _buttonPaintText,\
       WS_CHILD + WS_VISIBLE + WS_TABSTOP + BUTTON_BS_PUSHBUTTON,\
       0, 0, 0, 0,\
       [MainWindow], ID_BUTTON_DEMO, [wc.hInstance], 0

test    rax, rax
jz      error

mov     [hButton], rax

CreateWindowExW returns the button's own HWND. The parent is MainWindow, so Windows knows where notifications from this child must go.

Why create it at 0,0,0,0?

The source creates the child first, then applies the DPI-aware size and position in LayoutButton. Creation and layout stay separate.

3. The control ID gives the parent a stable identity

The button receives ID_BUTTON_DEMO as its child-control ID. The parent later receives this ID inside WM_COMMAND, allowing it to tell which child generated the notification.

constantsbutton identity
ID_BUTTON_DEMO         equ 1001
BUTTON_BS_PUSHBUTTON   equ 00000000h
BUTTON_BN_CLICKED      equ 0

The explicit names make the lesson easier to read: one value identifies which control, while another identifies what happened.

4. BN_CLICKED arrives inside WM_COMMAND

For a button notification, the parent receives WM_COMMAND. The low 16 bits of wParam hold the control ID, the high 16 bits hold the notification code, and lParam contains the child HWND.

WindowProcdecode WM_COMMAND
.wmcommand:
        mov     eax, dword [wparam]
        mov     ecx, eax

        ; LOWORD(wParam) -> control ID.
        and     eax, 0FFFFh
        cmp     eax, ID_BUTTON_DEMO
        jne     .default

        ; HIWORD(wParam) -> notification code.
        shr     ecx, 16
        cmp     ecx, BUTTON_BN_CLICKED
        jne     .default

Nothing special had to be added to the button's own window procedure. The standard BUTTON class handles mouse/keyboard interaction and sends the notification to its parent.

5. The click changes state — it does not paint

The important line in this tutorial is almost comically small:

WM_COMMAND / BN_CLICKEDapplication state
; Toggle our own state: 0 = no painted text, 1 = painted text visible.
xor     dword [TextVisible], 1

TextVisible belongs to our application, not to USER32. The click handler changes that state and leaves the actual rendering to WM_PAINT.

This separation scales well

A small demo toggles one Boolean. A real application might update a selection, document state, progress value, model object or view mode. The paint path then renders whatever the current state says should be visible.

6. InvalidateRect requests a repaint

After changing state, the source calls InvalidateRect.

WM_COMMANDrequest repaint
.request_repaint:
        ; InvalidateRect does not call PaintWindow directly. It marks the client
        ; area dirty; Windows later delivers WM_PAINT through the normal flow.
        invoke InvalidateRect, [hwnd], NULL, FALSE

        xor     eax, eax
        jmp     .finish

This distinction matters: InvalidateRect marks pixels as needing repaint. It does not mean “draw this text right now.” Windows coalesces paint work and later sends WM_PAINT when appropriate.

7. WM_PAINT renders the current state

The paint routine checks TextVisible. When it is zero, the text section is skipped. When it is nonzero, the source reuses the Unicode/GDI technique from Tutorial 02.

PaintWindowconditional rendering
cmp     dword [TextVisible], 0
je      .skip_painted_text

invoke GetClientRect, [hwnd], textRect

mov     eax, [ScaledTitleHeight]
mov     [textRect.top], eax

mov     eax, [ButtonY]
sub     eax, [ScaledTextButtonGap]
mov     [textRect.bottom], eax

invoke SelectObject, [hdc], [hTextFont]
mov     rdi, rax

invoke SetBkMode, [hdc], TRANSPARENT
invoke SetTextColor, [hdc], PAINT_TEXT_COLOR

invoke DrawTextW, [hdc], _paintText, -1, textRect,\
       DT_CENTER + DT_VCENTER + DT_SINGLELINE

invoke SelectObject, [hdc], rdi

.skip_painted_text:

The text rectangle ends above the button, so the lesson text and child control remain visually separate even after resizing.

8. The button owns its own caption

The button text changes from Paint Text to Clear Text as the state toggles. Because the caption belongs to the button window, the parent changes it with the normal Unicode window-text API.

WM_COMMANDSetWindowTextW
cmp     dword [TextVisible], 0
je      .hide_text

invoke SetWindowTextW, [hButton], _buttonClearText
jmp     .request_repaint

.hide_text:
        invoke SetWindowTextW, [hButton], _buttonPaintText

We do not paint over the button ourselves. Windows still owns the normal BUTTON appearance in this tutorial.

9. A real child control receives WM_SETFONT

Tutorial 02's painted text has no HWND, so its HFONT is selected into the parent HDC during painting. The button is different: it is a real child window, so we tell it which font to use with WM_SETFONT.

UpdateButtonFontchild-control font
mov     [hButtonFont], rsi
invoke SendMessageW, [hButton], WM_SETFONT, rsi, TRUE

The button stores the font handle but does not take ownership of the GDI object. Our application created the HFONT, so our application must eventually delete it.

Painted text HFONT -> SelectObject(HDC) Native BUTTON HFONT -> WM_SETFONT(HWND)

10. Child windows need layout, and DPI affects that layout

A child HWND does not automatically move to the center when its parent resizes. The application owns the layout policy, so WM_SIZE calls LayoutButton.

WM_SIZEre-layout child
.wmsize:
        call    LayoutButton
        invoke InvalidateRect, [hwnd], NULL, FALSE
        xor     eax, eax
        jmp     .finish

LayoutButton calculates a centered X position and a Y position slightly below the usable client center, leaving room for the conditional text above it.

LayoutButtonDPI-aware position
mov     eax, [rect.right]
sub     eax, [ScaledButtonWidth]
sar     eax, 1
mov     [ButtonX], eax

mov     eax, [rect.bottom]
sub     eax, [ScaledTitleHeight]
sub     eax, [ScaledButtonHeight]
sar     eax, 1
add     eax, [ScaledTitleHeight]
add     eax, [ScaledButtonOffsetY]
mov     [ButtonY], eax

invoke MoveWindow, [hButton], [ButtonX], [ButtonY],\
       [ScaledButtonWidth], [ScaledButtonHeight], TRUE

On WM_DPICHANGED, the source recalculates the scaled dimensions and recreates both application-owned fonts from their original 96-DPI design values.

11. The parent owns both HFONT objects

Window 1.4 owns two fonts: one for the conditional DrawTextW text and one given to the native button through WM_SETFONT. Both are explicitly deleted during WM_DESTROY.

WM_DESTROYfont ownership
cmp     [hTextFont], 0
je      .no_text_font
invoke DeleteObject, [hTextFont]
mov     [hTextFont], 0

.no_text_font:
cmp     [hButtonFont], 0
je      .no_button_font
invoke DeleteObject, [hButtonFont]
mov     [hButtonFont], 0

The native button window itself is a child of the top-level window, so USER32 destroys that HWND as part of destroying its parent. The GDI font handle is different: because we created it, we own its lifetime.

12. What we learned

One ordinary button gives us the central message flow used by many standard Win32 controls.

  • A native BUTTON is a child window with its own HWND.
  • The parent identifies the child through its control ID.
  • A click arrives at the parent as WM_COMMAND / BN_CLICKED.
  • LOWORD(wParam) identifies the control; HIWORD(wParam) identifies the notification.
  • Event handlers should change application state rather than paint directly.
  • InvalidateRect requests repaint work; WM_PAINT performs the rendering.
  • SetWindowTextW changes the native button's own Unicode caption.
  • A child control receives its font through WM_SETFONT.
  • The application still owns an HFONT it created, even after sending it to a control.
  • Child HWND layout must be updated when the parent size or DPI changes.
