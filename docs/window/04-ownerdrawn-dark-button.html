Tutorial 04 · Window

Owner-Drawn Dark Button

Window 1.4 already gave us the correct native button behavior. Now we keep that behavior and change only who paints the button. This is the key idea behind Win32 owner-draw.

1. One major change: painting responsibility

Tutorial 03 established the interaction model we want to keep: the child is a real native BUTTON, the parent receives WM_COMMAND / BN_CLICKED, application state changes, and WM_PAINT renders that state.

Window 1.5 does not replace that model. It changes one thing: the button asks its parent to draw the button face and caption.

Window 1.4 native BUTTON │ ├─ USER32 owns behavior ├─ focus / keyboard / mouse └─ BN_CLICKED │ ▼ Window 1.5 adds BS_OWNERDRAW │ ▼ WM_DRAWITEM │ ▼ parent paints appearance
The central rule

BS_OWNERDRAW changes painting responsibility. It does not turn the button into a custom control and it does not replace the system BUTTON window procedure.

2. BS_OWNERDRAW keeps the BUTTON but redirects painting

The creation call is almost identical to Tutorial 03. The important change is the button style.

maincreate the owner-drawn BUTTON
invoke CreateWindowExW, 0, ButtonClassName, _buttonPaintText,\
       WS_CHILD + WS_VISIBLE + WS_TABSTOP + BUTTON_BS_OWNERDRAW,\
       0, 0, 0, 0,\
       [MainWindow], ID_BUTTON_DEMO, [wc.hInstance], 0

The child HWND is still created from the system 'BUTTON' class. USER32 still handles focus, Space/Enter activation, mouse capture and click generation. The source comment says it directly: the style “only redirects the visual work to our parent's WM_DRAWITEM.”

3. WM_DRAWITEM goes to the parent

When an owner-drawn button needs to be displayed, Windows sends WM_DRAWITEM to the button's parent. The message's lParam points at a DRAWITEMSTRUCT describing what Windows wants drawn and where.

WindowProcroute WM_DRAWITEM
cmp     [wmsg], WM_DRAWITEM
je      .wmdrawitem
WM_DRAWITEMlParam points at DRAWITEMSTRUCT
.wmdrawitem:
        mov     rbx, [lparam]

This is different from WM_PAINT. We do not call BeginPaint for the button here. Windows already supplies the destination HDC inside the structure.

4. DRAWITEMSTRUCT needs the real Win64 layout

The supplied FASM.INC file does not expose a DRAWITEMSTRUCT definition, so this source defines a uniquely named local x64 layout rather than guessing with 32-bit offsets.

The pointer-sized fields are the important part. After five DWORD fields, x64 alignment inserts four bytes of padding before the first HWND. The complete structure is 40h bytes.

.datalocal Win64 structure
struct DRAWITEMSTRUCT64_LOCAL
  CtlType       dd ?             ; 00h
  CtlID         dd ?             ; 04h
  itemID        dd ?             ; 08h
  itemAction    dd ?             ; 0Ch
  itemState     dd ?             ; 10h
  pad0          dd ?             ; 14h -> align HWND
  hwndItem      dq ?             ; 18h
  hDC           dq ?             ; 20h
  rcItemLeft    dd ?             ; 28h
  rcItemTop     dd ?             ; 2Ch
  rcItemRight   dd ?             ; 30h
  rcItemBottom  dd ?             ; 34h
  itemData      dq ?             ; 38h
ends                              ; sizeof = 40h
Why the padding matters

Using a 32-bit structure layout in a 64-bit process would make fields after itemState land at the wrong offsets. The HDC, RECT and state information would then be read from the wrong bytes.

5. Identify exactly which control is asking to be drawn

A parent may eventually own several owner-drawn controls. The handler therefore checks more than one field before drawing.

WM_DRAWITEMvalidate the sender
cmp     dword [rbx + DRAWITEMSTRUCT64_LOCAL.CtlType], BUTTON_ODT_BUTTON
jne     .default

cmp     dword [rbx + DRAWITEMSTRUCT64_LOCAL.CtlID], ID_BUTTON_DEMO
jne     .default

mov     rax, [rbx + DRAWITEMSTRUCT64_LOCAL.hwndItem]
cmp     rax, [hButton]
jne     .default

The source checks the control type, the control ID and the exact child HWND. That is deliberately strict and makes the routine safe to extend later.

6. Paint the face from native button state

The button itself tells us whether it is currently selected/pressed through itemState. We do not maintain a duplicate mouse-down flag in our application.

WM_DRAWITEMnormal versus pressed face
mov     eax, [rbx + DRAWITEMSTRUCT64_LOCAL.itemState]
test    eax, BUTTON_ODS_SELECTED
jnz     .button_pressed

invoke CreateSolidBrush, BUTTON_COLOR_NORMAL
jmp     .have_button_fill

.button_pressed:
invoke CreateSolidBrush, BUTTON_COLOR_PRESSED
WM_DRAWITEMfill and frame
invoke FillRect, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], buttonRect, rsi

invoke CreateSolidBrush, BUTTON_COLOR_BORDER
invoke FrameRect, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], buttonRect, rsi

The normal face is #242424, close to the parent background, while the pressed face becomes a little lighter. A restrained border keeps the control visible without looking like a bright classic button.

7. Owner-draw does not change caption ownership

Windows no longer draws the caption for us, but the caption still belongs to the child HWND. That distinction is useful because Tutorial 03 already changes the caption between Paint Text and Clear Text with SetWindowTextW.

The drawing routine therefore asks the child for its current text instead of hard-coding a separate copy.

WM_DRAWITEMread the current BUTTON caption
invoke GetWindowTextW, [hButton], ButtonTextBuffer, BUTTON_TEXT_CAPACITY

invoke SelectObject, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], [hButtonFont]
mov     rdi, rax

invoke SetBkMode, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], TRANSPARENT

invoke DrawTextW, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], ButtonTextBuffer, -1,\
       buttonTextRect, DT_CENTER + DT_VCENTER + DT_SINGLELINE

This gives us one source of truth: the native child window owns the caption, and the owner-draw code merely renders whatever caption the child currently contains.

8. ODS_SELECTED gives us real pressed feedback

The source uses the same native ODS_SELECTED bit for both the button face and the caption treatment.

WM_DRAWITEMpressed caption color
mov     eax, [rbx + DRAWITEMSTRUCT64_LOCAL.itemState]
test    eax, BUTTON_ODS_SELECTED
jnz     .button_text_pressed

invoke SetTextColor, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC],\
       BUTTON_COLOR_TEXT_NORMAL
jmp     .draw_button_text

.button_text_pressed:
invoke SetTextColor, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC],\
       BUTTON_COLOR_TEXT_PRESSED
WM_DRAWITEMone-DPI-pixel pressed offset
invoke MulDiv, BUTTON_PRESSED_OFFSET_96, [CurrentDpi], 96
test    eax, eax
jnz     .pressed_offset_ready
mov     eax, 1

.pressed_offset_ready:
add     [buttonTextRect.left], eax
add     [buttonTextRect.top], eax
add     [buttonTextRect.right], eax
add     [buttonTextRect.bottom], eax

The pressed caption uses the same blue as our tutorial/site accent: RGB #58A6FF. The one-pixel shift is calculated from the 96-DPI design value so it remains visually consistent at higher DPI.

No duplicate pressed flag

Because ODS_SELECTED comes from the native BUTTON, this feedback follows native mouse capture and keyboard activation automatically.

9. Keyboard focus still belongs to the native control

An owner-drawn control should not silently remove keyboard feedback. The native button exposes focus through ODS_FOCUS, and the source draws an inset focus rectangle when that bit is present.

WM_DRAWITEMfocus cue
mov     eax, [rbx + DRAWITEMSTRUCT64_LOCAL.itemState]
test    eax, BUTTON_ODS_FOCUS
jz      .button_draw_done

invoke InflateRect, buttonFocusRect, [FocusInsetNeg], [FocusInsetNeg]
invoke DrawFocusRect, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], buttonFocusRect

This is another good example of owner-draw preserving behavior: Windows tracks focus, and our code decides how that state is represented visually.

10. The WM_DRAWITEM HDC is borrowed

The HDC in DRAWITEMSTRUCT is supplied by Windows. The routine may select the application-owned button font into it temporarily, but it should restore the previous object before returning.

WM_DRAWITEMrestore the supplied DC
invoke SelectObject, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], [hButtonFont]
mov     rdi, rax

; ... draw caption ...

invoke SelectObject, [rbx + DRAWITEMSTRUCT64_LOCAL.hDC], rdi

The temporary brushes created for the face and border are also deleted after use. The same ownership discipline from the earlier GDI lessons still applies.

11. WM_COMMAND and BN_CLICKED stay the same

This is the most important proof that owner-draw did not replace the control's behavior. The click handler from Tutorial 03 is still the mechanism that toggles TextVisible and updates the button caption.

WM_COMMANDbehavior remains native
and     eax, 0FFFFh
cmp     eax, ID_BUTTON_DEMO
jne     .default

shr     ecx, 16
cmp     ecx, BUTTON_BN_CLICKED
jne     .default

xor     dword [TextVisible], 1
WM_COMMANDrequest parent and child repaint
invoke InvalidateRect, [hwnd], NULL, FALSE
invoke InvalidateRect, [hButton], NULL, FALSE

The parent invalidation updates the conditional DrawTextW text. The child invalidation requests a fresh owner-draw pass for the button. These are separate windows with separate update regions.

native BUTTON behavior │ ├─ BN_CLICKED ──► WM_COMMAND ──► application state │ └─ visual state ─► WM_DRAWITEM ─► custom appearance

12. What we learned

Owner-draw becomes much easier to reason about once behavior and appearance are kept separate.

  • BS_OWNERDRAW keeps the native BUTTON class and redirects its painting.
  • WM_DRAWITEM is sent to the parent, not the child.
  • lParam points at a DRAWITEMSTRUCT.
  • The x64 structure needs pointer alignment and is 40h bytes in this source.
  • The handler can validate CtlType, CtlID and hwndItem.
  • ODS_SELECTED supplies the real native pressed state.
  • ODS_FOCUS supplies native keyboard-focus state.
  • The child HWND still owns its caption; GetWindowTextW retrieves it for drawing.
  • The HDC supplied through WM_DRAWITEM is borrowed and should have its previous GDI objects restored.
  • Temporary brushes created by the application must be deleted.
  • WM_COMMAND / BN_CLICKED remains the interaction path from Tutorial 03.
  • Owner-draw changes appearance without replacing native control behavior.
