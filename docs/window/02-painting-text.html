Painting Text with DrawTextW

The base shell already knows how to exist, paint, move, resize and scale. Now we make one important change: paint Unicode text directly into the window with GDI — without creating a child control.

1. One new idea

Tutorial 01 built the reusable top-level shell. This lesson deliberately leaves that working behavior alone and adds one new responsibility: drawing text during WM_PAINT.

The source version is Window 1.3.1. The extra .1 records the small refinement made before publishing: the painted lesson text uses the same restrained blue accent as the website, while the high-contrast resize grip from the base shell remains unchanged.

2. DrawTextW paints pixels — it does not create a control

This distinction is the heart of the lesson. A native STATIC control would be another window with its own HWND. It would participate in message routing, layout and control font messages.

DrawTextW does something much simpler: it receives a device context and paints glyphs into it. There is no new child window and therefore no text-control handle to store.

Why this matters

If the painted area becomes invalid, Windows sends WM_PAINT again. Our code must redraw the text. The pixels are the result of painting; they are not a persistent control object.

STATIC control

A real child HWND. Windows owns control behavior and sends the parent notifications/messages as appropriate.

DrawTextW

A GDI drawing operation against an HDC. No child HWND exists.

3. The text is Unicode data

The project continues to use the wide-character path. In FASM, du stores UTF-16 code units, which is exactly what DrawTextW expects.

.dataUTF-16 strings
_paintText      du 'Painted with DrawTextW', 0
_textFontName   du 'Segoe UI', 0

The terminating zero matters because the call passes -1 as the character count. That tells DrawTextW to treat the string as null-terminated.

4. Painted text needs an application-owned HFONT

A child control can receive a font through WM_SETFONT. Painted text has no child HWND, so there is nothing to send WM_SETFONT to.

Instead, the program creates an HFONT, stores it in hTextFont, and selects that font into the paint HDC immediately before drawing.

maincreate the initial text font
; Create the application-owned font used by our painted text.
; This is NOT a control font: there is no child HWND involved.
call    UpdateTextFont
cmp     [hTextFont], 0
je      error

Because CreateFontW creates the object, the application owns that object and must eventually release it with DeleteObject.

5. Why the font height is negative

The source scales the 96-DPI design height and then negates it before calling CreateFontW.

UpdateTextFontDPI-scaled font creation
invoke MulDiv, TEXT_FONT_HEIGHT_96, [CurrentDpi], 96
neg     eax
mov     [ScaledTextFontHeight], eax

invoke CreateFontW, [ScaledTextFontHeight], 0, 0, 0, FW_NORMAL,\
       FALSE, FALSE, FALSE, DEFAULT_CHARSET, OUT_DEFAULT_PRECIS,\
       CLIP_DEFAULT_PRECIS, DEFAULT_QUALITY, DEFAULT_PITCH + FF_DONTCARE,\
       _textFontName

For CreateFontW, a negative height asks GDI to match the character height rather than the complete character-cell height. That makes the requested visual size more predictable for this lesson.

The replacement font is created first. Only after a valid new handle exists does the routine replace and delete the old one, so a failed recreation does not destroy the last working font.

6. The painted-text sequence inside WM_PAINT

The normal shell paint begins with BeginPaint, fills the dark background, draws the title strip and close button, then reaches the new text section.

PaintWindowpainted Unicode text
invoke GetClientRect, [hwnd], textRect

mov     eax, [ScaledTitleHeight]
mov     [textRect.top], eax

invoke SelectObject, [hdc], [hTextFont]
mov     rdi, rax

invoke SetBkMode, [hdc], TRANSPARENT
invoke SetTextColor, [hdc], PAINT_TEXT_COLOR

invoke DrawTextW, [hdc], _paintText, -1, textRect,\
       DT_CENTER + DT_VCENTER + DT_SINGLELINE

invoke SelectObject, [hdc], rdi

That compact block contains the full lesson: choose a drawing rectangle, select the font, choose background and text behavior, draw the Unicode text, and restore the previous GDI state.

7. DrawTextW needs a layout rectangle

GetClientRect gives us the full client area. The source then moves only textRect.top below the custom title strip.

PaintWindowexclude the title strip
invoke GetClientRect, [hwnd], textRect

; Keep the text out of our custom title strip.
mov     eax, [ScaledTitleHeight]
mov     [textRect.top], eax

With DT_CENTER + DT_VCENTER + DT_SINGLELINE, DrawTextW centers the single line horizontally and vertically inside that remaining rectangle.

8. COLORREF is BGR, not RGB

The painted text uses the website accent color #58A6FF. The Win32 API does not receive that value in ordinary web-style RGB byte order.

constantsblue painted text
; Painted client text color.
; COLORREF byte order is 00BBGGRR, so 00FFA658h = RGB #58A6FF.
PAINT_TEXT_COLOR      equ 00FFA658h

A Win32 COLORREF is laid out as 00BBGGRR. For RGB #58A6FF, red is 58, green is A6, and blue is FF, producing 00FFA658h.

Easy mistake to make

Writing 0058A6FFh would not mean “#58A6FF” to SetTextColor. The red and blue byte positions are reversed in a COLORREF.

9. Restore the previous GDI object

SelectObject returns the object that was previously selected into the HDC. The source saves that handle in RDI and restores it after DrawTextW.

PaintWindowHDC state discipline
invoke SelectObject, [hdc], [hTextFont]
mov     rdi, rax

...

invoke DrawTextW, [hdc], _paintText, -1, textRect,\
       DT_CENTER + DT_VCENTER + DT_SINGLELINE

; Leave the DC exactly as we received it.
invoke SelectObject, [hdc], rdi

This is the same ownership discipline used for the grip pen. A device context has selected GDI objects as part of its state. Temporary drawing code should not leave that state altered accidentally.

10. DPI changes mean recreating the font

The shell already recalculates title, close-button, border and grip dimensions when WM_DPICHANGED arrives. Window 1.3.1 extends that rule to the painted font.

WM_DPICHANGEDrecreate from the 96-DPI baseline
movzx   eax, word [wparam]
mov     [CurrentDpi], eax

call    UpdateScaledValues

; Recreate the painted-text font from its original 96-DPI design height.
call    UpdateTextFont

TEXT_FONT_HEIGHT_96 remains the stable design value. The program does not scale an already-scaled height again, which avoids accumulating rounding error as the window moves between monitors.

11. Delete the font during WM_DESTROY

The new resource adds one new cleanup responsibility. The font is application-owned, so WM_DESTROY releases it before posting the quit message.

WM_DESTROYHFONT cleanup
cmp     [hTextFont], 0
je      .no_text_font

invoke DeleteObject, [hTextFont]
mov     [hTextFont], 0

.no_text_font:

DrawTextW does not take ownership of the font merely because the font was selected into the paint HDC. Creation and destruction remain our responsibility.

12. The resize grip and shell stay intact

This lesson does not replace the borderless-shell behavior from Tutorial 01. The same high-contrast three-line grip is still painted in the bottom-right corner, and WM_NCHITTEST still returns HTBOTTOMRIGHT for its full rectangle.

That is an important learning pattern for this project: keep known-good behavior and add one concept at a time. Here the new concept is painted text, not another rewrite of moving or resizing.

13. What we learned

Painting text directly is a small visual change, but it introduces several Win32 ideas that become useful again in owner drawing and custom controls.

  • DrawTextW paints into an HDC; it does not create a child control.
  • UTF-16 text can be stored with FASM du and passed directly to the wide API.
  • Painted text needs an application-owned HFONT selected into the paint HDC.
  • A negative CreateFontW height requests character height.
  • DT_CENTER + DT_VCENTER + DT_SINGLELINE centers one line inside a rectangle.
  • SetBkMode(..., TRANSPARENT) prevents GDI from painting an opaque text background rectangle.
  • Win32 COLORREF values use 00BBGGRR byte order.
  • Temporary GDI selections should be restored before leaving the paint operation.
  • DPI changes require recreating size-dependent GDI objects from the original 96-DPI baseline.
  • Objects created by the application must be explicitly deleted.
