Tutorial 01 · Window

Building the Base Win64 Window Shell

Before a ListView, TreeView, button or status bar can exist, we need the thing that owns them: a real top-level Windows window, a message loop, a window procedure and a clean set of rules for painting, resizing and DPI changes.

1. The starting point

This source is intentionally a window shell, not a control demo. There are no child controls here. That is useful because every later example can add one new control without also introducing all of the machinery needed to make the parent window exist.

Why does the file say “Window 1.2”?

The shell existed first, and the visible bottom-right resize grip was refined afterward. The version number therefore says 1.2, but conceptually this is lesson one: the clean base window used underneath the later control examples.

The key design decision is WS_POPUP. A normal framed window asks Windows to draw and manage its standard caption and sizing frame. A popup window removes that normal non-client frame, so this example paints a dark title strip itself and tells USER32 where its invisible resize zones are.

our code │ ├─ registers a window class ├─ creates a WS_POPUP top-level window ├─ paints the dark shell └─ answers hit-test questions │ ▼ USER32 │ ├─ runs the native move loop └─ runs the native resize loop

2. Program entry

The executable enters at main. The first instruction adjusts the stack before API calls are made, then the process opts into Per-Monitor-V2 DPI awareness.

maininitial setup
main:
        ; Keep RSP correctly aligned for Win64 calls made through invoke.
        sub     rsp, 8

        invoke SetProcessDpiAwarenessContext, DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2

        invoke GetModuleHandleW, 0
        mov     [wc.hInstance], rax

        invoke LoadIconW, 0, IDI_APPLICATION
        mov     [wc.hIcon], rax
        mov     [wc.hIconSm], rax

        invoke LoadCursorW, 0, IDC_ARROW
        mov     [wc.hCursor], rax

        invoke CreateSolidBrush, 001E1E1Eh
        test    rax, rax
        jz      error
        mov     [wc.hbrBackground], rax

GetModuleHandleW, 0 returns the current executable module handle. That instance handle is stored in the window-class structure and later passed to CreateWindowExW.

The dark class brush is created by this program, so the program owns it. That ownership matters later during destruction.

3. Registering the window class

Before Windows can create a window of our custom class, USER32 needs a description of that class. The source declares a WNDCLASSEX structure in the data section and points its window-procedure field at WindowProc.

.dataWNDCLASSEX
wc WNDCLASSEX sizeof.WNDCLASSEX, CS_HREDRAW + CS_VREDRAW, WindowProc, 0, 0, NULL, NULL, NULL, COLOR_BTNFACE + 1, NULL, _class, NULL

RegisterClassExW does not create a visible window. It registers a recipe: class name, procedure, cursor, icons and other class-wide information.

WNDCLASSEX │ ▼ RegisterClassExW │ ▼ USER32 knows the class │ ▼ CreateWindowExW can instantiate it

4. Creating the top-level window

The actual window appears when the program calls CreateWindowExW with the registered class name and the WS_POPUP style.

mainCreateWindowExW
invoke CreateWindowExW, 0, _class, _title,\
       WS_POPUP,\
       [WinX], [WinY], [WinW], [WinH],\
       0, 0, [wc.hInstance], 0

test    rax, rax
jz      error

mov     [MainWindow], rax

Because WS_POPUP removes the normal caption and sizing frame, the shell must provide its own title-strip painting and hit testing. But it can still ask USER32 to perform the real move and resize operations.

5. The message loop

A GUI program does not normally poll the mouse and keyboard itself. Windows places messages in the GUI thread's queue, and the application retrieves and dispatches them.

mainmessage pump
.message_loop:
        invoke GetMessageW, msg, 0, 0, 0
        cmp     eax, 1
        jb      end_loop
        jne     .message_loop

        invoke TranslateMessage, msg
        invoke DispatchMessageW, msg
        jmp     .message_loop
GetMessageW │ ▼ thread message queue │ ├─ TranslateMessage └─ DispatchMessageW │ ▼ WindowProc

Later, PostQuitMessage causes the loop to terminate cleanly.

6. WindowProc: where Windows talks to us

Windows calls WindowProc whenever the window needs to react to a message. Under the Windows x64 calling convention the first four integer or pointer arguments arrive in RCX, RDX, R8 and R9.

WindowProcmessage dispatch
proc WindowProc uses rbx rsi rdi, hwnd, wmsg, wparam, lparam

        mov     [hwnd], rcx
        mov     [wmsg], rdx
        mov     [wparam], r8
        mov     [lparam], r9

        cmp     [wmsg], WM_PAINT
        je      .wmpaint

        cmp     [wmsg], WM_LBUTTONDOWN
        je      .wmlbuttondown

        cmp     [wmsg], WM_NCHITTEST
        je      .wmnchittest

        cmp     [wmsg], WM_SIZE
        je      .wmsize

        cmp     [wmsg], WM_DPICHANGED
        je      .wmdpichanged

        cmp     [wmsg], WM_DESTROY
        je      .wmdestroy

.default:
        invoke DefWindowProcW, [hwnd], [wmsg], [wparam], [lparam]

The default path is important. Messages the program does not explicitly handle are forwarded to DefWindowProcW, preserving the standard Windows behavior we have not chosen to replace.

7. Native resizing without a standard frame

This is the central trick behind the borderless shell. For WM_NCHITTEST, Windows asks: what part of the window is under this screen coordinate?

WM_NCHITTESTbottom-right grip
.wmnchittest:
        ; lParam contains signed 16-bit SCREEN coordinates.
        movsx   eax, word [lparam]
        movsx   edx, word [lparam + 2]

        mov     [pt.x], eax
        mov     [pt.y], edx

        invoke ScreenToClient, [hwnd], pt
        invoke GetClientRect, [hwnd], rect

        mov     eax, [pt.x]
        mov     edx, [pt.y]

        ; Test the visible grip first.
        mov     ecx, [rect.right]
        sub     ecx, [ScaledGripSize]
        cmp     eax, ecx
        jl      .normal_border_test

        mov     ecx, [rect.bottom]
        sub     ecx, [ScaledGripSize]
        cmp     edx, ecx
        jl      .normal_border_test

        mov     eax, HTBOTTOMRIGHT
        jmp     .finish

The full handler also returns HTLEFT, HTRIGHT, HTTOP, HTBOTTOM and the corner variants. Returning one of these values hands the interaction back to USER32.

The important design idea

We are not writing our own resize loop. We define the invisible resize zones; Windows performs the native sizing operation.

The visible grip is tested before the ordinary border because it is deliberately larger. The drawn target and the real mouse target therefore match.

8. Painting the dark shell

WM_PAINT calls PaintWindow. Painting begins with BeginPaint and ends with EndPaint.

PaintWindowmain paint sequence
invoke BeginPaint, [hwnd], ps
mov     [hdc], rax

invoke GetClientRect, [hwnd], rect
invoke FillRect, [hdc], rect, [wc.hbrBackground]

; Custom title strip
mov     dword [rect.left], 0
mov     dword [rect.top], 0
mov     eax, [ScaledTitleHeight]
mov     [rect.bottom], eax

invoke CreateSolidBrush, 00262626h
mov     [brush], rax
...
invoke FillRect, [hdc], rect, [brush]
invoke DeleteObject, [brush]
...
invoke EndPaint, [hwnd], ps

The source paints the dark client background, the custom title strip and close button, and finally three diagonal lines for the bottom-right resize grip.

The grip itself is only a visual representation. The resize behavior comes from WM_NCHITTEST. Painting describes what the region looks like; hit testing tells Windows what that region means.

9. Close-button and title-drag behavior

WM_LBUTTONDOWN only reaches this code for client-area clicks. The handler first tests the custom close-button rectangle, then checks whether the click occurred in the title strip.

HandleMouseClicknative caption drag
invoke PostMessageW, [hwnd], WM_CLOSE, 0, 0
...
.not_close:
        mov     eax, [ScaledTitleHeight]
        cmp     [MouseY], eax
        jg      .done

        invoke ReleaseCapture
        invoke SendMessageW, [hwnd], WM_NCLBUTTONDOWN, HTCAPTION, 0

The program does not implement its own drag loop. Sending WM_NCLBUTTONDOWN with HTCAPTION tells USER32 to treat the custom strip like a normal caption. Native move behavior, including snapping, remains in Windows.

10. Per-monitor DPI scaling

All shell dimensions begin as 96-DPI design values. UpdateScaledValues recalculates them from that fixed baseline using MulDiv.

UpdateScaledValues96-DPI baseline
proc UpdateScaledValues

        invoke MulDiv, TITLE_HEIGHT_96, [CurrentDpi], 96
        mov     [ScaledTitleHeight], eax

        invoke MulDiv, CLOSE_BTN_SIZE_96, [CurrentDpi], 96
        mov     [ScaledCloseBtnSize], eax

        invoke MulDiv, BORDER_SIZE_96, [CurrentDpi], 96
        mov     [ScaledBorderSize], eax

        invoke MulDiv, GRIP_SIZE_96, [CurrentDpi], 96
        mov     [ScaledGripSize], eax

        ret
endp

Scaling always starts from the original 96-DPI constants rather than repeatedly scaling already-scaled values. That avoids accumulated rounding error when the window moves between monitors.

On WM_DPICHANGED, the new DPI is stored, the dimensions are recalculated and the rectangle recommended by Windows is applied with SetWindowPos.

11. GDI ownership: delete what you create

Native Windows code becomes easier to reason about when handle ownership stays explicit.

CreateSolidBrush / CreatePen

The application creates these GDI objects, so the application is responsible for deleting them.

Selected GDI objects

The grip pen is replaced with the previous DC object before DeleteObject is called.

Class background brush

It lives for the shell's lifetime and is released during WM_DESTROY.

PostQuitMessage

It terminates the message loop; it is not a GDI resource and requires no deletion.

WM_DESTROYcleanup
.wmdestroy:
        ; Delete only objects that THIS application created.
        cmp     [wc.hbrBackground], 0
        je      .no_background_brush

        invoke DeleteObject, [wc.hbrBackground]
        mov     [wc.hbrBackground], 0

.no_background_brush:
        invoke PostQuitMessage, 0
        xor     eax, eax

12. What we learned

Even an “empty” native window already teaches most of the machinery that every later control example depends on.

  • A custom window class connects a class name to a window procedure and shared class resources.
  • CreateWindowExW creates the actual top-level window.
  • The thread message queue is the central event-delivery mechanism.
  • WindowProc handles selected messages and forwards the rest to DefWindowProcW.
  • A borderless WS_POPUP can still use native Windows move and resize behavior.
  • Painting and hit testing are separate responsibilities.
  • DPI measurements are recalculated from a stable 96-DPI baseline.
  • GDI object ownership must remain explicit.
